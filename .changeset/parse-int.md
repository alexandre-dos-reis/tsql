Compile `Number.parseInt`. `Number.parseInt(s)` reads a leading `0x` as hexadecimal, as TypeScript does, and `Number.parseInt(s, 10)` does not and so stops at the `x`; both return a `Float`, because the result can be `NaN` and is not bounded by 32 bits. It is a parser rather than a cast — the prefix is read and the rest ignored, so `parseInt("12abc")` is `12` where `'12abc'::integer` raises — and the SQL was measured against V8 on 48 inputs through both forms: whitespace, signs, trailing garbage, `-0`, the rounding ties past 2^53, the exact boundary where a double becomes `Infinity`, and a 200,001-digit argument. Three places a naive translation would have diverged are closed: overflow *raises* in PostgreSQL where JavaScript gives `Infinity`, `numeric` has no negative zero, and an `0x` prefix with no digits after it is `NaN` rather than `0`. Refused with a message: any other radix, a radix that is not a literal, and every other member of `Number` — `Number.isNaN` now says to write `x !== x`, and `Number.isInteger` to write `Math.floor(x) === x`, instead of being refused as an unnamed runtime global.

Adds the `tsql.parse_int` and `tsql.parse_int_10` helpers, which takes the runtime to **revision 2**. No existing helper changed its body, so nothing a `Math` function returned before changes now; a migration installs the new helpers only when a compiled function calls them.
